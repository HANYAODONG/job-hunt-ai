# 岗位池与人岗匹配原则

## 一、核心关系

岗位池不是“每个 JD 一个岗位”，而是用标准化的功能岗位对真实招聘市场进行归类。

```text
三级功能岗位：后端开发工程师
    ├── Java开发工程师 JD
    ├── Go开发工程师 JD
    ├── Python后端开发工程师 JD
    └── 服务端开发工程师 JD
```

- 一级岗位：较宽的技术/职业领域。
- 二级岗位：领域内的岗位方向或岗位族。
- 三级岗位：现实中可识别的功能型岗位，是岗位池的标准分类边界。
- JD：企业发布的一条具体招聘信息，是最终被推荐和匹配的对象。
- 专长/技术栈：Java、Go、Python、Spring Boot、MySQL 等，用于区分同一功能岗位下的具体 JD。

一个三级岗位可以覆盖很多真实 JD，但不能把所有 JD 都机械地拆成独立三级岗位。

## 二、为什么采用这种结构

如果把 Java 后端、Go 后端、Python 后端全部当成互斥三级岗位，岗位池会按语言、框架、行业或城市机械膨胀。这样会把实际相近的岗位误判为不同岗位，放大人工标注与系统预测之间的假性错误。

如果只保留“后端开发工程师”并停止在这个层级，匹配又会过于粗糙，无法判断候选人是否适合某个具体技术栈岗位。

因此要把两个维度分开：

> 三级岗位回答“这个人主要做什么工作”；专长和 JD 要求回答“他适合哪一条具体招聘信息”。

## 三、人岗匹配的正确链路

```text
简历
  -> 判断功能岗位方向
  -> 在对应岗位池中检索真实 JD
  -> 比较技能、职责、经验、学历、地点等要求
  -> 对技术栈和硬性要求进行差异化评分
  -> 返回具体真实 JD，并显示其标准三级岗位
```

例如，Java + Spring Boot + MySQL 的简历：

- 对 Java 后端 JD：功能方向和技术栈都匹配，应优先推荐。
- 对 Go 后端 JD：功能方向相同，但核心技术栈不同，应降低匹配分。
- 对数据工程 JD：即使也要求 Python 或 SQL，也不能仅凭技能重叠归入后端岗位。

最终展示可以是：

```text
推荐岗位：Java后端开发工程师
标准三级岗位：后端开发工程师
技术栈匹配：Java、Spring Boot、MySQL、Redis
```

## 四、岗位池建设原则

1. 三级岗位名称必须是现实招聘市场可识别的岗位名称，不能创造抽象或幻觉岗位。
2. 三级岗位按稳定的工作职能划分，而不是按编程语言、城市、行业或单一工具划分。
3. 每条 JD 必须保留真实标题、职责、技能、经验等原始信息，并映射到一个标准三级岗位。
4. 标题相近但职责不同的岗位要分开；标题不同但职责和能力要求高度相近的岗位可以归入同一三级岗位。
5. 无法可靠映射的 JD 进入审核队列，不能为了提高覆盖率静默塞入正式岗位池。
6. 岗位池覆盖的是功能岗位空间；具体招聘覆盖率由该三级岗位下的真实 JD 数量和来源多样性体现。

## 五、测试集设计原则

测试集以“简历-JD 对”为核心，而不是只测试“简历-三级岗位”分类。

每条测试样本建议同时包含：

- 简历文本和技能；
- 真实 JD 标题、职责和要求；
- 标准三级岗位 ID；
- 技术栈匹配、硬性条件和总体匹配结果；
- 人工解释或证据。

必须覆盖以下难例：

- 同一功能岗位、不同语言或框架；
- 不同功能岗位、部分技能重叠；
- 标题不同但实际职责相同；
- 标题相同但职责明显不同；
- 邻近岗位之间的边界案例。

## 六、验收标准

岗位池和匹配系统只有同时满足以下条件，才能作为全景图谱和人岗匹配的共同底座：

- 三级岗位名称现实可识别；
- 岗位之间边界清晰、交集可解释；
- 能覆盖新一代信息技术/IT 的主要功能岗位；
- 每个正式三级岗位都有真实 JD 和技能证据；
- 匹配结果能够落到具体真实 JD，而不是停留在三级岗位名称；
- 技术栈差异会影响匹配分数，但不会被误当成完全不同的职业；
- 金标、图谱、检索和匹配使用同一套稳定的 `canonical_role_id`。
