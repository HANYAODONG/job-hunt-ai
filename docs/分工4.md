# 第四阶段分工：前端对接与全链路验收

## 1. 阶段定位

上一阶段已经完成了后端主链路的初步整合：

- 标准数据产物可以由 `scripts/dataset_adapter.py` 生成。
- BM25、Semantic/BGE、技能图谱、融合排序等模块已经有独立接口或服务雏形。
- 后端新增了统一推荐入口：

```text
POST /api/v1/fusion/recommend
```

因此第四阶段不再优先拆分新的算法功能，而是先解决一个核心问题：

```text
前端页面能否稳定调用后端统一接口，并展示真实推荐结果、分项得分和解释信息。
```

动态知识图谱、权重调优、消融实验继续保留为后续增强项，但当前优先级低于前后端连通。

## 2. 本阶段总目标

本阶段结束时，项目至少要跑通下面这条演示链路：

```text
用户打开前端页面
  -> 输入求职需求或选择样例
  -> 前端调用 /api/v1/fusion/recommend
  -> 后端返回 TopN 岗位推荐
  -> 前端展示岗位信息、总分、分项得分、匹配技能、缺失技能和推荐理由
```

验收时优先使用 `mode=sample`，保证不同成员电脑上都可以稳定跑通。  
等页面对接稳定后，再逐步切换到 `mode=offline` 或 `mode=online`。

## 3. 统一端口和接口约定

### Docker 启动后的访问地址

```text
前端页面:     http://localhost:18080
后端 API:     http://localhost:18088
后端文档:     http://localhost:18088/docs
Elasticsearch: http://localhost:9200
Neo4j:         http://localhost:7474
```

### 前端调用方式

前端代码中不要再硬编码：

```text
http://localhost:8000/api/v1
```

统一使用：

```text
/api/v1
```

原因是：

- Docker 中前端容器通过代理访问 `backend:8000`。
- 浏览器只需要访问前端自身域名，不需要关心后端容器地址。
- 本地 npm 启动时，代理默认转发到 `http://localhost:18088`。

### 推荐主接口

前端优先对接：

```text
POST /api/v1/fusion/recommend
```

请求示例：

```json
{
  "query_text": "熟悉 Python、SQL，有后端开发和数据处理经验，希望找数据工程师岗位",
  "top_k": 20,
  "candidate_pool": 50,
  "mode": "sample"
}
```

返回字段重点使用：

```text
results[].job_id
results[].final_score
results[].score_breakdown
results[].explanation
results[].meta
```

## 4. 分工安排

### 工作 1：前端 API 服务层对接

负责人：前端对接同学

任务：

1. 在 `frontend-src/src/services/fusionApi.js` 中统一封装 `recommendJobs()`。
2. 页面不要直接拼接口路径。
3. 错误时显示明确提示，而不是空白页面。
4. 保留 Mock 模式，但真实接口模式必须默认可用。

验收：

- 页面调用 `/api/v1/fusion/recommend` 成功。
- 浏览器控制台没有跨域错误。
- 后端日志能看到 `POST /api/v1/fusion/recommend 200 OK`。

### 工作 2：Fusion 演示页接入统一推荐

负责人：前端页面同学

任务：

1. 将 `FusionDemoPage` 的“BM25 真实检索”调整为“统一推荐接口”。
2. 默认使用 `mode=sample` 联调。
3. 展示后端返回的：
   - 岗位标题
   - 公司
   - 地点
   - 总匹配分
   - BM25 / Semantic / Skill / Graph 分项得分
   - 匹配技能和缺失技能
   - 推荐解释
4. 保留离线融合结果和 Demo Mock 两种辅助模式。

验收：

- 访问 `http://localhost:18080/fusion-demo`。
- 输入查询文本后点击“统一推荐”。
- 页面能展示推荐卡片和分项解释。

### 工作 3：主搜索页后续迁移

负责人：主搜索页同学

任务：

1. 先不急着重构 `/search` 页面。
2. 等 `fusion-demo` 跑稳后，再决定是否把 `/search` 的搜索按钮也切到 `/fusion/recommend`。
3. 当前 `/search` 可继续保留旧岗位搜索逻辑，避免一次性改动过大。

验收：

- `/search` 不因为本轮改动出现回归。
- 后续迁移时只改 service 层和数据映射层。

### 工作 4：后端接口稳定性

负责人：后端整合同学

任务：

1. 保证 `/api/v1/fusion/recommend` 在 `sample` 模式下稳定返回结果。
2. 缺少 BGE 模型、semantic index 或完整 KG 产物时，接口不能直接崩溃。
3. 保证返回结构适合前端展示。
4. 补充必要的接口说明和联调文档。

验收：

```powershell
Invoke-RestMethod `
  -Uri "http://localhost:18088/api/v1/fusion/recommend" `
  -Method Post `
  -ContentType "application/json" `
  -Body '{"query_text":"熟悉 Python 和 SQL，希望找数据分析岗位","top_k":5,"candidate_pool":20,"mode":"sample"}'
```

能返回 `results`，且 `results` 内包含 `final_score`、`score_breakdown`、`explanation`、`meta`。

## 5. 本阶段暂不优先做的事

下面这些不是放弃，而是放到前端对接跑通之后：

- 动态知识图谱随时间演化。
- 全量 BGE-M3 向量索引构建。
- 大规模消融实验。
- 权重自动调优。
- 企业评分标准深度建模。

原因是这些功能都依赖一条稳定的主链路。主链路没打通之前继续扩功能，会增加联调成本。

## 6. 当前优先级

```text
P0: 前端能调用 /fusion/recommend 并展示结果
P1: Docker、本地 npm 两种启动方式端口一致
P2: 返回字段和前端卡片展示对齐
P3: 主搜索页逐步迁移到统一推荐入口
P4: online/offline 模式替换 sample 模式
P5: 动态知识图谱和实验增强
```

## 7. 本阶段完成标志

满足下面条件后，可以认为第四阶段完成：

1. `docker compose up -d` 后前端和后端都能访问。
2. `http://localhost:18080/fusion-demo` 能调用真实后端接口。
3. 推荐卡片能展示岗位 meta、总分、分项得分和解释。
4. 后端 sample 模式、offline 模式、mock 模式边界清晰。
5. 组员可以按同一套命令部署并复现页面效果。
