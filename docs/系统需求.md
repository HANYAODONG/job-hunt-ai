## 1. 文档目的

本文用于记录团队已经讨论形成的产品方向，避免后续设计和开发偏离赛题。

本文只确定以下内容：

- 系统解决什么问题。
- 系统主要服务哪些用户。
- 求职者端和企业端分别承担什么职责。
- 整套系统应形成怎样的业务闭环。
- 前端需要呈现哪些核心功能页面。
- 比赛时应如何讲清楚系统价值。

本文暂不确定具体接口、数据库结构、算法实现、字段定义和测试方案。这些内容应在产品方向确认后分别形成技术方案和实施计划。

## 2. 对赛题的核心理解

本赛题要求的不是普通招聘网站，也不是单纯的知识图谱展示工具。

系统真正要解决的问题是：岗位市场变化很快，但岗位标准、人才评价和求职者学习方向之间缺少持续更新的统一依据。

因此，系统需要持续获取最新岗位信息，发现新岗位和能力变化，将其维护为可信的岗位能力图谱，再使用这套图谱服务求职者发展和企业招聘。

完整业务闭环是：

```text
获取最新岗位信息
→ 发现新岗位与岗位能力变化
→ 人工审核和优化岗位定义
→ 更新岗位能力图谱
→ 解析求职者或候选人的能力
→ 完成人岗匹配与差距分析
→ 输出改进建议和学习路径
```

## 3. 产品定位

### 3.1 一句话定位

一套以动态岗位能力图谱为底座，同时服务求职者职业发展与企业人才招聘的双角色智能平台。

### 3.2 产品主线

系统默认以求职者体验作为主要叙事：

> 帮助求职者看懂岗位最新要求，了解自己与目标岗位的真实差距，并获得可以执行的提升路径。

企业端则负责岗位知识的治理和招聘应用：

> 帮助企业发现岗位变化、维护岗位标准，并基于统一标准辅助人才筛选和评估。

### 3.3 产品形态

比赛阶段采用一套前端工程，通过角色切换呈现求职者端和企业端。

两端不是两套彼此割裂的产品，而是共享同一个岗位知识底座：

```text
动态岗位能力图谱
├─ 求职者端：岗位认知 → 自我诊断 → 成长改进
└─ 企业端：岗位发现 → 人工治理 → 招聘匹配
```

## 4. 用户与职责

### 4.1 求职者

求职者主要关注“我适合什么岗位、还缺什么、接下来应该怎么提升”。

求职者可以：

- 浏览岗位体系和最新能力要求。
- 按技术方向和岗位级别探索岗位。
- 上传简历并确认个人能力画像。
- 选择目标岗位进行匹配诊断。
- 查看优势、差距和原因解释。
- 获得针对性的改进建议和学习路径。

求职者只能查看已经发布的岗位信息，不能修改岗位标准。

### 4.2 企业用户

企业用户包括岗位专家、招聘人员和审核人员，主要关注“岗位要求是否准确、候选人是否匹配”。

企业用户可以：

- 查看系统发现的新岗位和岗位能力变化。
- 查看变化趋势、数据来源和原始依据。
- 修改和优化岗位名称、职责、技能及应用场景。
- 审核并发布新的岗位定义或岗位版本。
- 使用同一套岗位标准评估候选人。

企业端不是简单地在求职者页面增加编辑按钮。它还承担证据审核、岗位治理、版本发布和招聘匹配等职责。

## 5. 两端共享的核心能力

求职者端和企业端共享以下基础能力：

- 岗位库
- 岗位能力图谱
- 岗位层级和技术栈分类
- 岗位能力要求
- 岗位版本与变化记录
- 简历解析和个人能力画像
- 人岗匹配与差距分析
- 结论解释和来源证据

两端的差异主要体现在使用目的、首页内容、导航结构、信息深度和操作权限，而不是维护两套重复数据。

## 6. 核心产品能力

### 6.1 新岗位发现与定义

系统持续分析市场中的岗位信息，识别尚未标准化但正在出现或快速增长的新岗位。

新岗位定义至少需要表达：

- 岗位名称
- 核心职责
- 必备技能
- 加分技能
- 典型行业应用场景

系统先形成候选定义，再由企业人员查看依据、人工优化并发布。

### 6.2 既有岗位能力动态更新

系统持续识别现有岗位能力要求的变化，例如某项技能被新增、删除、强化或弱化。

企业人员需要能够看到：

- 发生了什么变化。
- 为什么认为发生了变化。
- 变化来自哪些市场信息。
- 人工调整后最终发布了什么内容。

已发布的历史岗位信息应被保留，使后续匹配结果能够说明当时使用的是哪一版岗位要求。

### 6.3 岗位全景图谱

图谱应以分层方式表达岗位与技能之间的关系：

```text
岗位大类 → 岗位族 → 具体岗位 → 技能点
```

用户可以从较大的技术领域逐层进入具体岗位，并按技术栈和岗位级别切换视图。

图谱的作用不是单纯展示复杂关系，而是帮助用户理解：

- 某个领域包含哪些岗位。
- 不同岗位之间有什么联系。
- 一个岗位需要哪些具体技能。
- 初级、中级和高级岗位要求有什么差异。
- 当前市场正在出现哪些新变化。

### 6.4 人岗匹配与差距分析

用户上传简历或补充技能信息后，系统形成个人能力画像，并与目标岗位的最新已发布要求进行比较。

诊断结果应回答：

- 当前整体匹配程度如何。
- 已经具备哪些关键能力。
- 缺失或不足的能力是什么。
- 哪些差距最影响求职结果。
- 系统为什么得出这些结论。

同一套能力也可以在企业端用于候选人评估，但系统只提供辅助判断，不替代企业最终招聘决策。

### 6.5 改进建议与学习路径

系统应根据具体能力差距生成建议，而不是输出通用的学习文案。

学习路径需要体现：

- 先补什么、后补什么。
- 每个阶段解决哪个能力差距。
- 建议完成怎样的学习或项目实践。
- 完成后如何再次验证能力变化。

## 7. 前端功能页面

### 7.1 求职者端

```text
首页
岗位探索
全景图谱
我的能力
人岗诊断
学习路径
```

求职者首页应优先呈现目标岗位、最近诊断、关键差距和学习进度，不展示企业内部审核和数据治理内容。

### 7.2 企业端

```text
企业工作台
市场信号
岗位管理
岗位图谱
人才匹配
数据与评测
```

企业工作台应优先呈现待审核的新岗位、待确认的能力变化、证据不足项目和最近发布记录。

### 7.3 角色切换

比赛版本可以在账号区域提供“求职者端 / 企业端”切换入口。

切换角色后应更换首页、导航和可执行操作，但保持统一的视觉语言和共享的岗位数据。

## 8. 信息展示原则

系统界面首先要简洁、直观，不能为了展示技术而把所有指标同时堆在页面上。

技术细节采用逐级展开：

```text
第一层：用户需要知道的结论
第二层：得出结论的主要原因
第三层：数据来源、原文证据和处理过程
```

例如，默认先展示“模型评测已成为该岗位的必备技能”，用户进一步查看时再展示市场频次变化、样本来源和原始岗位描述。

求职者端强调易懂和行动建议；企业端允许查看更完整的证据和技术细节。

## 9. 比赛演示主线

比赛展示应讲述一个完整故事，而不是依次打开互不关联的页面。

### 第一部分：求职者获得什么

1. 求职者通过岗位图谱发现目标岗位。
2. 查看岗位最新职责、技能要求和市场变化。
3. 上传简历并确认个人能力。
4. 获得匹配度、优势和关键差距。
5. 根据差距生成改进建议和学习路径。

### 第二部分：岗位信息从哪里来

1. 切换到企业端。
2. 展示系统发现的新岗位或既有岗位变化。
3. 查看趋势、来源和原始依据。
4. 企业人员人工修改、审核并发布岗位信息。
5. 发布结果进入岗位库和全景图谱。

### 第三部分：如何服务企业招聘

1. 企业选择已经发布的招聘岗位标准。
2. 导入候选人简历并查看匹配结果。
3. 查看候选人的优势、风险和关键差距。
4. 说明企业与求职者使用的是同一套岗位标准和匹配能力。

## 10. 当前阶段的范围

现阶段优先保证以下方向能够形成完整展示闭环：

- 双角色入口和差异化页面。
- 一个新岗位发现、人工优化和发布案例。
- 一个既有岗位能力更新案例。
- 可逐层探索到技能点的岗位图谱。
- 简历解析、能力确认和人岗诊断。
- 针对差距生成改进建议和学习路径。
- 结论能够展开查看来源和依据。

现阶段不扩展为完整招聘管理系统、在线教育平台、求职社区或企业人力资源系统。

## 11. 赛题硬性要求

赛题提出的准确率、测试样本量和单元测试覆盖率等指标必须在后续技术方案中承接，但不在本文中提前确定实现方式。

前端当前只需为这些指标预留清晰、可信的展示位置，并保证展示内容能够追溯到实际评测结果。

进入页面设计和实施计划前，还需要继续确认：

## 13. 方向总结

本系统不是“招聘网站加一个知识图谱”，也不是“企业后台加一个求职页面”。

它的核心是持续更新的岗位能力标准：

```text
市场变化形成岗位知识
岗位知识形成统一标准
统一标准同时服务求职成长与企业招聘
```

比赛版本采用一套前端实现双角色体验。求职者端负责表达系统对个人的直接价值，企业端负责证明岗位知识如何产生、如何被治理，以及如何用于招聘决策。
