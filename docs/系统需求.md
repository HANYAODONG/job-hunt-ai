> 赛题编号：XH-202621  
> 赛题名称：多源异构数据驱动岗位和能力图谱构建与动态演化分析研究  
> 出题单位：科大讯飞股份有限公司  
> 文档版本：v0.1  
> 文档状态：需求基线讨论稿，待团队确认  
> 更新时间：2026-07-26

## 1. 文档目的

本文用于统一团队对赛题、系统定位、用户角色、功能边界、数据流和比赛演示方式的理解，避免前后端在开发过程中把系统做成若干互不关联的功能页面。

本文首先回答五个问题：

1. 系统主要服务谁？
2. 求职者端和企业端分别解决什么问题？
3. 两端共享哪些底层能力？
4. 岗位数据如何产生、审核、发布并用于人岗匹配？
5. 比赛阶段最少需要完成怎样的闭环？

### 1.1 当前决策记录

以下内容是本轮讨论已经形成的产品共识，后续如有调整，应直接更新本文而不是只保留在聊天记录中：

1. 系统采用“求职者端 + 企业端”的双角色定位，默认叙事和主要价值出口面向求职者。
2. 比赛阶段只维护一套前端工程，通过角色切换、导航、权限和信息密度区分两端体验。
3. 两端共享同一套岗位库、岗位能力图谱、岗位版本、证据链和人岗匹配引擎。
4. 企业端不只是给求职者页面增加编辑按钮，还要承担市场信号审核、岗位定义维护、版本发布和招聘匹配。
5. 求职者只能使用已发布的岗位标准进行探索、诊断和学习规划，不能修改岗位定义。
6. 岗位图谱采用“岗位大类 → 岗位族 → 具体岗位 → 技能点”的分层结构，并支持技术栈和岗位级别切换。
7. 页面默认保持简洁直观，模型置信度、来源、原文片段和处理记录等技术细节通过逐级展开呈现。
8. 现有后端接口必须保留；尚未实现的能力可以先采用 mock 数据，但接口结构应按照本文的领域对象设计。

以下内容在进入正式实施计划前仍需团队确认：

- P0 功能范围是否符合最终答辩时长和团队开发资源。
- 求职者首页与企业工作台的具体页面布局和视觉方向。
- 比赛演示使用的新岗位、既有岗位更新和求职者简历样例。

## 2. 赛题理解

赛题要求建设的并不是普通招聘网站，也不是单纯的知识图谱展示系统，而是一套能够持续感知岗位市场变化，并将最新岗位能力要求应用到人才诊断中的完整系统。

赛题要求的业务闭环为：

```text
多源岗位数据采集
→ 新岗位发现与既有岗位能力更新
→ 人工审核与岗位版本发布
→ 岗位能力图谱动态更新
→ 简历解析与用户能力画像
→ 人岗匹配与差距分析
→ 针对性改进建议与学习路径规划
```

其中存在两类不同的使用者：

- 求职者是岗位知识、诊断结果和学习建议的主要使用者。
- 企业岗位专家、招聘人员或审核人员是岗位知识的维护者和招聘匹配结果的使用者。

因此，本系统应当被设计为“双角色、单底座”的产品，而不是两套完全独立的系统。

## 3. 产品定位

### 3.1 一句话定位

一套以动态岗位能力图谱为知识底座，同时服务求职者职业发展与企业人才招聘的双角色智能平台。

### 3.2 核心价值

对求职者：

> 让求职者看懂岗位最新要求，知道自己与目标岗位之间的真实差距，并获得可以执行的改进路径。

对企业：

> 让企业持续维护贴近市场实际的岗位能力标准，并使用统一标准提高招聘与人才评估的准确性。

### 3.3 产品主次关系

比赛展示和默认产品体验以求职者为主要叙事，企业端负责解释岗位知识如何被发现、审核、修改和发布。

```text
求职者端：主要体验和价值出口
企业端：岗位知识治理与招聘应用
系统底座：数据采集、模型、图谱、证据和版本
```

### 3.4 产品形态

比赛阶段使用一套前端工程和一套设计系统，通过用户角色控制导航、页面入口和操作权限。

- 未登录或求职者角色默认进入求职者端。
- 企业角色进入企业工作台。
- 两端复用岗位库、岗位详情、图谱和匹配引擎。
- 只有企业角色能够修改、审核和发布岗位信息。
- 求职者只能查看已经发布的岗位版本，不能修改岗位标准。

## 4. 用户角色

### 4.1 求职者

典型任务：

- 浏览新一代信息技术领域的岗位体系。
- 了解不同岗位、技术栈和级别的最新能力要求。
- 上传简历或手动补充技能信息。
- 选择目标岗位并进行人岗匹配诊断。
- 查看优势、能力缺口和证据解释。
- 获取针对性改进建议和学习路径。
- 完成学习任务后重新诊断。

### 4.2 企业岗位专家

典型任务：

- 查看系统识别出的新岗位候选。
- 查看既有岗位的能力变更候选。
- 检查岗位结论的数据来源和原始证据。
- 修改岗位名称、职责、技能和应用场景。
- 审核并发布岗位版本。
- 查看岗位版本历史和能力变化。

### 4.3 企业招聘人员

典型任务：

- 选择企业招聘岗位及其能力版本。
- 查看候选人与岗位的匹配结果。
- 查看候选人的优势、风险和关键能力缺口。
- 对多个候选人进行统一标准下的比较。
- 将匹配结论作为招聘辅助信息，而不是替代人工决策。

### 4.4 系统管理员或评测人员

典型任务：

- 管理数据来源和采集任务。
- 查看数据时效、重复率、有效率和异常记录。
- 查看 JD 解析、简历解析和匹配模型的评测结果。
- 检查低置信度结论、错误样本和幻觉防控记录。

## 5. 双端能力边界

| 能力 | 求职者端 | 企业端 |
|---|---|---|
| 浏览岗位库 | 可以 | 可以 |
| 浏览全景岗位图谱 | 可以 | 可以 |
| 按技术栈、级别筛选 | 可以 | 可以 |
| 查看岗位最新能力要求 | 可以 | 可以 |
| 查看岗位版本历史 | 可查看摘要 | 可查看完整记录和证据 |
| 上传和解析简历 | 可以 | 可以，用于候选人评估 |
| 人岗匹配与差距分析 | 面向本人 | 面向候选人或员工 |
| 改进建议 | 可以 | 可以查看候选人建议摘要 |
| 学习路径规划 | 可以 | 可用于员工发展场景 |
| 查看新岗位候选 | 不可以 | 可以 |
| 查看岗位变更候选 | 不可以 | 可以 |
| 修改岗位定义 | 不可以 | 可以 |
| 审核和发布岗位版本 | 不可以 | 仅审核角色可以 |
| 查看原始 JD 和处理记录 | 仅查看必要解释 | 可以查看完整证据链 |
| 数据治理与模型评测 | 不可以 | 管理员和评测人员可以 |

## 6. 共享知识底座

求职者端和企业端不维护两套岗位数据。所有功能共享以下核心对象：

### 6.1 岗位大类

新一代信息技术领域的最高层分类，例如：人工智能、大数据、智能系统、物联网。

### 6.2 岗位族

同一业务或技术方向下的一组岗位，例如：大模型应用、算法研究、数据平台、工业物联网。

### 6.3 岗位

经过标准化的具体岗位，例如：AI Agent 应用工程师、Java 开发工程师。

### 6.4 岗位定义

至少包含：

- 岗位名称
- 核心职责
- 必备技能
- 加分技能
- 典型行业应用场景
- 所属岗位大类和岗位族
- 适用级别

### 6.5 能力项

岗位要求的最小技能点。能力项应包含：

- 标准名称
- 近义词和别名
- 能力类别
- 要求等级
- 必备或加分属性
- 市场需求强度
- 来源证据

### 6.6 岗位版本

岗位定义每次正式发布后形成不可修改的版本，例如 `v1.0`、`v1.1`。

新修改必须生成新的草稿和版本，不能直接覆盖已发布版本。

### 6.7 市场信号

系统从招聘数据和行业材料中识别出的潜在变化，包括：

- 新岗位候选
- 既有岗位变更候选
- 新增能力候选
- 删除能力候选
- 能力要求等级变化
- 岗位名称和职责边界变化

### 6.8 证据

所有岗位结论都应尽可能关联以下信息：

- 数据来源
- 原始文本片段
- 采集时间
- 数据有效性
- 去重和交叉验证状态
- 模型置信度
- 人工审核记录

### 6.9 用户能力画像

由简历解析结果和用户确认信息共同组成，包括技能、项目、工作经历、教育经历及其证据。

### 6.10 诊断报告

用户能力画像与指定岗位版本的比较结果。诊断报告必须记录所使用的岗位版本，保证结果可复现。

### 6.11 学习计划

针对能力缺口生成的有顺序、有前置关系、可跟踪进度的改进任务。

## 7. 求职者端功能需求

### 7.1 求职者首页

首页应直接服务求职任务，不展示企业审核队列和数据治理信息。

主要内容：

- 当前目标岗位
- 最近一次匹配度
- 最重要的能力缺口
- 当前学习计划进度
- 热门岗位和新兴岗位
- 进入岗位图谱、上传简历和继续学习的快捷入口

### 7.2 岗位探索

用户可以：

- 搜索岗位名称和技能。
- 按领域、技术栈、岗位级别和市场热度筛选。
- 查看岗位职责、技能要求和行业应用场景。
- 查看岗位需求变化趋势。
- 比较两个岗位之间的能力差异。
- 将岗位设为目标岗位并发起诊断。

### 7.3 全景岗位图谱

图谱层级至少支持：

```text
岗位大类 → 岗位族 → 具体岗位 → 技能点
```

图谱必须支持：

- 节点展开和收起。
- 按技术栈切换视图。
- 按初级、中级、高级切换要求。
- 查看岗位与技能点之间的关联。
- 查看岗位当前发布版本。
- 从岗位节点进入岗位详情或发起诊断。
- 在移动端提供可用的简化探索方式。

### 7.4 简历解析与能力画像

用户可以上传 PDF、DOC 或 DOCX 简历。

系统应：

- 提取技能、项目、经历和教育信息。
- 展示每项提取结果的置信度和原文证据。
- 允许用户确认、删除或补充提取结果。
- 生成结构化用户能力画像。
- 明确说明隐私和数据处理方式。

简历技能提取准确率目标不低于 90%。

### 7.5 人岗匹配诊断

用户选择一个具体岗位和一个已发布岗位版本后发起诊断。

诊断结果至少包括：

- 综合匹配度
- 技术基础匹配
- 核心技能匹配
- 项目实践匹配
- 工程化能力匹配
- 行业经验匹配
- 已满足能力项
- 缺失能力项
- 能力等级不足项
- 诊断结论解释
- 简历证据与岗位要求证据

匹配准确率目标不低于 90%。

### 7.6 改进建议

建议不能只给出泛化文案，应与具体能力缺口建立关联。

每条建议至少包含：

- 对应能力缺口
- 缺口优先级
- 为什么需要补齐
- 建议的练习或项目
- 预期产出
- 完成后如何重新验证

### 7.7 学习路径规划

学习路径应包含：

- 阶段顺序
- 前置依赖
- 阶段目标
- 学习任务
- 推荐项目实践
- 预期交付物
- 预计耗时
- 完成状态
- 重新诊断入口

学习路径必须能追溯到诊断缺口和目标岗位版本。

## 8. 企业端功能需求

### 8.1 企业工作台

企业工作台聚焦待处理任务：

- 新岗位候选数量
- 岗位变更候选数量
- 待补充证据项目
- 待审核岗位草稿
- 最近发布的岗位版本
- 数据更新时间和质量风险

### 8.2 市场信号中心

统一管理两类市场信号：

- 新岗位候选
- 既有岗位变更候选

企业人员可以：

- 查看信号强度和变化趋势。
- 查看岗位样本数量和数据来源。
- 查看技能共现、岗位名称聚类等系统解释。
- 查看原始 JD 片段。
- 接受候选、退回补证或拒绝候选。

### 8.3 岗位定义工作台

企业岗位专家可以编辑：

- 岗位名称
- 所属岗位大类和岗位族
- 核心职责
- 必备技能
- 加分技能
- 典型行业应用场景
- 不同岗位级别的能力要求

编辑界面应同时展示来源证据，防止人工修改与市场事实脱离。

### 8.4 既有岗位能力更新

系统应明确显示两个版本之间的差异：

- 新增能力项
- 删除能力项
- 修改能力项
- 必备和加分属性变化
- 能力等级变化
- 变更原因
- 支撑本次变化的数据来源

企业人员可以修改变更内容并提交审核。

### 8.5 岗位审核与发布

岗位草稿状态至少包括：

```text
系统候选 → 编辑中 → 待审核 → 已发布
                    ↘ 退回补证
```

发布后：

- 形成不可修改的岗位版本。
- 更新岗位库和岗位能力图谱。
- 新诊断默认使用最新发布版本。
- 历史诊断继续引用原岗位版本。

### 8.6 企业人才匹配

为体现“解决企业招聘与人岗匹配痛点”，企业端应提供最小可用的人才匹配视图。

至少支持：

- 选择招聘岗位及岗位版本。
- 上传一份或多份候选人简历。
- 查看候选人匹配度和关键差距。
- 按统一岗位标准比较候选人。
- 查看系统结论依据。
- 标注结果仅用于辅助决策。

比赛最小版本可先完整演示单个候选人的诊断，多候选人比较作为增强功能。

### 8.7 数据治理与评测

企业管理员或评测人员可以查看：

- 数据源覆盖量
- 数据更新时间
- 重复率和抄袭聚类结果
- 数据清洗和标准化记录
- 交叉验证状态
- 低置信度能力项
- JD 解析准确率
- 简历技能提取准确率
- 人岗匹配准确率
- 错误样本和修正记录

## 9. 核心数据流程

### 9.1 岗位知识生产流程

```text
招聘网站、企业官网、行业报告和技术社区
→ 数据采集
→ 清洗、去重、时效处理和来源标准化
→ JD 结构化解析
→ 岗位名称、职责、技能和场景抽取
→ 岗位聚类、趋势检测和变化检测
→ 新岗位候选或岗位变更候选
→ 人工审核和编辑
→ 发布岗位版本
→ 更新岗位库和能力图谱
```

### 9.2 求职者成长流程

```text
浏览岗位图谱
→ 选择目标岗位及版本
→ 上传简历
→ 解析并确认能力画像
→ 人岗匹配
→ 查看优势和能力缺口
→ 生成改进建议
→ 生成学习路径
→ 完成任务并重新诊断
```

### 9.3 企业招聘流程

```text
企业选择招聘岗位及版本
→ 导入候选人简历
→ 生成候选人能力画像
→ 统一标准下进行匹配
→ 查看候选人优势、缺口和风险
→ 人工完成招聘判断
```

### 9.4 结果追溯链

系统中的重要结论应支持以下追溯：

```text
学习任务
→ 改进建议
→ 能力缺口
→ 岗位能力项
→ 岗位版本
→ 岗位定义或变更记录
→ 原始市场证据
```

### 10.3 角色切换

比赛版本建议在顶部账号区域提供“求职者端 / 企业端”切换入口。

角色切换后：

- 保持同一套视觉语言。
- 根据角色更换首页和导航。
- 复用岗位库、岗位详情和图谱组件。
- 根据权限显示或隐藏编辑、审核和发布操作。
- 不在求职者页面展示企业内部治理数据。

## 11. 信息展示原则

所有技术结论采用三级信息层级：

```text
第一层：结论
第二层：为什么得到该结论
第三层：原始数据和处理记录
```

例如岗位能力变化默认展示：

```text
模型评测由加分技能调整为必备技能
需求频次近 90 天上升 21%
```

用户进一步展开后再查看：

- 样本数量
- 来源分布
- 原始 JD 片段
- 模型置信度
- 人工审核记录

求职者端强调清晰易懂，企业端允许查看更完整的技术细节。

## 12. 权限原则

### 12.1 求职者权限

- 只能读取已发布岗位版本。
- 可以编辑自己的能力画像。
- 可以生成和管理自己的诊断报告与学习计划。
- 不能修改岗位定义、证据和图谱关系。

### 12.2 企业编辑权限

- 可以创建和修改岗位草稿。
- 可以处理市场信号。
- 不能直接修改已经发布的历史版本。

### 12.3 企业审核权限

- 可以审核、退回和发布岗位版本。
- 发布行为必须记录审核人与时间。

### 12.4 管理员权限

- 可以管理数据源、评测集和系统任务。
- 可以查看完整处理记录和错误样本。

## 13. 比赛阶段最小闭环

比赛版本必须完整演示以下内容：

1. 系统从多源数据中发现一个新岗位，例如“AI Agent 应用工程师”。
2. 企业人员查看趋势、技能聚类和原始证据。
3. 企业人员修改岗位职责、技能和应用场景。
4. 审核并发布新岗位 `v1.0`。
5. 新岗位进入岗位库和全景图谱。
6. 系统识别一个既有岗位的能力变化，例如“Java 开发工程师”。
7. 展示新增、删除和修改能力项及其证据。
8. 企业人员审核并发布新版本。
9. 求职者浏览岗位图谱并选择目标岗位。
10. 求职者上传简历并确认能力画像。
11. 系统对照目标岗位版本完成人岗匹配。
12. 展示多维匹配度、优势、缺口和解释证据。
13. 根据缺口生成针对性建议和学习路径。

## 14. 推荐答辩演示顺序

建议采用求职者优先的演示叙事：

### 第一幕：求职者看到什么

1. 从岗位探索或全景图谱发现目标岗位。
2. 查看岗位最新职责、技能和市场变化。
3. 上传简历并确认系统提取的技能。
4. 查看匹配度和关键能力缺口。
5. 生成学习路径。

### 第二幕：这些岗位数据从哪里来

1. 切换到企业端。
2. 展示新岗位发现和既有岗位变化。
3. 展示多源证据、去重、交叉验证和置信度。
4. 人工修改并发布岗位版本。
5. 图谱实时更新。

### 第三幕：如何服务企业招聘

1. 企业选择同一个岗位版本。
2. 查看候选人的匹配报告。
3. 说明求职者和企业使用的是同一岗位标准与匹配引擎。
4. 展示准确率和测试集结果。

## 15. 非功能需求

### 15.1 可解释性

- 所有岗位变化必须有证据来源。
- 所有诊断缺口必须能解释岗位要求和用户现状。
- AI 生成内容必须标注状态和置信度。

### 15.2 可追溯性

- 诊断报告绑定岗位版本。
- 岗位发布保留版本历史。
- 人工修改和审核行为保留记录。

### 15.3 准确性

- JD 解析准确率不低于 90%。
- 简历技能提取准确率不低于 90%。
- 人岗匹配准确率不低于 90%。

### 15.4 数据质量

- 支持来源时效性检查。
- 支持重复和抄袭内容识别。
- 支持多源交叉验证。
- 支持低置信度结论进入人工审核。

### 15.5 用户体验

- 默认界面简洁，不一次展示全部技术指标。
- 图谱交互流畅，支持层级钻取。
- 差距分析必须清晰区分当前能力和岗位要求。
- 求职者和企业端使用一致的概念与视觉语言。
- 移动端至少保证求职者核心流程可用。

### 15.6 性能与部署

- 前端核心页面应在普通比赛演示环境中稳定运行。
- 图谱应避免因节点数量过多导致页面卡顿。
- 项目应提供容器化或明确部署说明。
- 后端暂未完成的能力可由 mock 接口演示，但接口结构必须与领域模型一致。

### 15.7 测试

- 至少准备 100 条岗位 JD 和对应测试用例。
- 单元测试覆盖率目标不低于 60%。
- 固定一组标注简历用于技能提取评测。
- 固定一组专家判断结果用于匹配准确率评测。
- 演示数据至少覆盖一个新岗位和一个既有岗位更新案例。

## 16. 前端接口边界

前端不直接感知大模型、聚类算法或知识图谱构建实现细节，而是使用稳定的业务接口。

### 16.1 市场信号接口

- 查询新岗位和岗位变更候选
- 查看候选详情和证据
- 保存人工修改草稿
- 提交审核、退回和发布

### 16.2 岗位库接口

- 查询岗位
- 获取岗位定义
- 获取当前版本和历史版本
- 比较两个岗位版本

### 16.3 图谱接口

- 根据领域、技术栈、级别和版本加载图谱投影
- 查询节点详情和关系证据

### 16.4 能力画像与诊断接口

- 上传和解析简历
- 确认用户能力画像
- 对指定岗位版本创建诊断
- 查询诊断解释和证据

### 16.5 学习计划接口

- 根据诊断报告生成学习计划
- 查询阶段任务和前置依赖
- 更新任务进度
- 发起重新诊断

## 17. 开发优先级

### P0：比赛闭环必须完成

- 双角色导航和权限差异
- 一个新岗位发现、编辑和发布案例
- 一个既有岗位能力更新案例
- 岗位库与岗位版本
- 技能点级全景图谱
- 简历解析和能力画像确认
- 人岗匹配与差距分析
- 针对性建议和学习路径
- 证据链和评测指标展示

### P1：增强产品可信度

- 多岗位和多级别筛选
- 岗位对比
- 多候选人比较
- 用户诊断历史
- 学习计划进度与重新诊断
- 完整数据源管理和错误样本分析

### P2：真实产品扩展

- 企业自定义岗位体系
- 企业人才库和招聘流程集成
- 学习资源推荐与课程接入
- 多租户、组织和细粒度权限
- 大规模图谱性能优化

## 18. 当前明确不做

比赛阶段暂不把以下能力作为核心范围：

- 完整招聘 ATS 系统
- 面试安排、Offer 和入职流程
- 在线课程平台和课程交易
- 企业组织架构和绩效管理
- 求职社交和内容社区
- 为求职者开放岗位标准编辑权限

这些能力与赛题闭环关系较弱，容易稀释产品定位。

## 19. 产品方向总结

本系统不是“企业后台加一个求职页面”，也不是“求职网站加一个图谱”。

正确的系统结构是：

```text
动态岗位能力图谱作为共同知识底座
             ↓
求职者端：岗位认知 → 自我诊断 → 成长改进
企业端：岗位发现 → 人工治理 → 招聘匹配
```

两端共享岗位、技能、版本、证据和匹配引擎，但具有不同的首页、导航、信息密度、操作权限和业务目标。

比赛版本采用一套前端工程实现双角色体验，既满足完整性和技术创新展示，又避免为演示目的维护两套重复代码。
