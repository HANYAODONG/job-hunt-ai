# 月度 JD 导入与新岗位审核流程

## 可上传文件

在前端“岗位演化中心 -> 批量新岗位发现”点击“导入月度 JD”，上传 CSV。最少需要一列岗位名称，推荐使用以下字段：

```text
job_id,month,job_title,responsibility,requirement,source
```

字段说明：

- `job_id`：原始岗位 ID；没有时系统会生成内部 ID。
- `month`：数据所属月份，格式建议为 `YYYY-MM`。
- `job_title`：原始招聘岗位名称，必填。
- `responsibility`：岗位职责。
- `requirement`：岗位要求和技能。
- `source`：来源名称或批次名称。

可直接使用的功能验证数据：

`artifacts/discovery_synthetic_fixture/synthetic_new_role_jds.csv`

这 12 条数据只用于验证新岗位发现闭环，不代表真实市场数据。

## 页面流程

1. 导入 CSV 后，系统以“人工模式”逐条处理并保留在审核队列。
2. 已有岗位的 JD 归入现有三级岗位；不能稳定归类的 JD 保留 `potential_new_job` 状态。
3. 批量页按候选岗位标题聚类，使用独立 JD ID 去重计数。
4. 去重后的同类 JD 数量大于 10 时，候选显示为“待人工审核”。
5. 在候选卡点击“审核并定义岗位”，再填写二级方向、三级岗位名称、匹配关键词、核心技能、核心职责、加分技能、应用场景和证据说明。页面会显示本次关联的独立 JD 证据数。
6. 点击“提交为新岗位”后，系统创建一份维护审核记录，并关联该候选簇内全部来源 JD；这一步不会立即改变正式数据。
7. 候选卡变为“发布到岗位池”后，人工复核岗位命名和职责边界，再点击发布。系统会将同一维护记录关联的全部来源 JD 写入运行时岗位目录；也可以驳回候选。

## 审核判断

- 归入现有岗位：岗位核心职责与已有三级岗位一致，只是技术栈、行业场景或市场标题不同。
- 提交为新岗位：候选岗位有稳定且独立的职责边界，并且与现有三级岗位无法仅靠“专长”字段表达其差异。
- 驳回候选：标题通胀、重复抓取、职责不足或尚未形成稳定市场需求。

“发布到岗位池”只更新运行时 JD 更新目录。正式 `canonical_role_pool_v2`、BM25、向量索引和 KG 仍须按版本切换流程另行审核与重建。

## LLM 是可选项

月度 JD 的导入、标题清洗和进入审核队列不要求配置 DeepSeek 密钥。没有密钥时，系统使用保守的本地标题规则，并将需要 LLM 的技能抽取延后到审核阶段；配置密钥后才启用 LLM 标题清洗、技能抽取和中间置信度二次裁决。

## 当前发布边界

当前发布接口会把审核通过的名称和分类写入公司 JD 更新模块使用的运行时标准岗位字典，并保留原始 JD 审核记录、备份和更新结果。

它不会自动修改 `artifacts/canonical_role_pool_v2/canonical_roles.csv`、`canonical_jobs.jsonl` 或已经生成的 BM25、向量、KG 产物。若新岗位要进入人岗匹配和全景图谱的 canonical v2 闭集，还需要算法组执行一次 canonical role 映射、索引/图谱增量重建和版本切换。

因此，“发布到岗位池”在当前页面上指运行时 JD 更新岗位目录；canonical v2 的正式合并仍需单独审核，避免未经复核的新岗位直接污染匹配闭集。
